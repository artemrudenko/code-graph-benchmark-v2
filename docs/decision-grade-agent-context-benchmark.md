# Практический benchmark: когда постоянный code context действительно нужен агенту

## Решение, которое должен поддержать стенд

Нужно решить не «какой инструмент победил», а другой вопрос:

> Сохраняет ли дополнительный индекс качество изменений по сравнению с прямой
> навигацией модели по актуальному исходнику и даёт ли измеримую пользу на
> повторяющейся работе?

Baseline — это не модель в вакууме. В baseline агенту доступны обычный поиск,
чтение файлов и запуск разрешённых тестов. Сравнивается этот рабочий способ с
добавочным постоянным контекстом: LSP-навигацией, графом или структурным
поиском, если он подходит задаче.

Индекс имеет право на использование только при двух условиях:

1. он не ухудшает корректность патча и не скрывает риск; и
2. на выбранной серии задач даёт заранее определённую, измеримую пользу:
   меньше повторного поиска, контекста, повторов или общего времени с учётом
   сборки и обновления.

Если первое условие не выполнено, второе не имеет значения. Если первое
выполнено, но выгоды нет, индекс не окупает свой жизненный цикл.

## Что проверять

### Гипотеза A — корректность

Агент с индексом выполняет фиксированное изменение не хуже source baseline.
Корректность определяется не красивым ответом и не LLM judge, а контрактом:
ожидаемое поведение, исходный код, тест, отрицательная мутация теста и граница
diff.

### Гипотеза B — устойчивость контекста

После изменения исходников индекс либо обновляется и показывает новую связь,
либо явно сообщает, что его данные stale/partial. Агент не должен использовать
старую карту как полный список связей.

### Гипотеза C — окупаемость

Только среди корректных запусков постоянный контекст уменьшает суммарную
работу на серии независимых задач. Считается всё: первичная сборка, refresh,
контекст модели, tool calls, retries и elapsed time. Порог значимой выгоды
нужно записать до запуска, исходя из вашего бюджета и скорости работы; также
нужно публиковать абсолютные значения, а не только проценты.

## Рекомендуемый основной кандидат: Info Radar

Для первого прикладного кейса берём собственный продукт Info Radar на
зафиксированной приватной ревизии. В нём есть Python-пайплайн, схема и
контрактные порты, React/TypeScript-интерфейс, а также детерминированные фейки
и офлайн-тесты. Поэтому можно проверить не только поиск имени, а понимание пути
изменения между слоями.

В эксперимент входит только отдельный чистый клон и существующие fixtures.
Не входят production Supabase, внешний сбор источников, OAuth, SMTP/Telegram,
реальные LLM-провайдеры, учётные данные и персональные данные. `core/` в этом
репозитории vendored и не должен быть мишенью задач.

Первый набор task card нужно собрать из одного закреплённого поведения, а не
из живой проблемы:

1. **Граница статуса доставки.** Проследить и безопасно изменить правило от
   Python-порта/адаптера и `docs/schema.sql` до React-проверки readiness. Истина:
   offline Python tests, TypeScript/Vitest tests и source review прав доступа.
2. **Зона регрессии.** Изменить небольшое правило пайплайна и назвать тесты,
   которые доказывают сохранение важного поведения. Истина: заранее подготовленный
   mutation и фиксированный набор офлайн-fixtures.
3. **Малый cross-module refactor.** Изменить один контракт без дублирования
   логики и сохранить путь `port → fake/adapter → consumer`. Истина: contract
   tests, типовая проверка frontend и ручная проверка diff.

Эти задачи не нужно писать как оценку самого Info Radar. Они нужны для ответа
на практический вопрос: помогает ли постоянный индекс агенту сохранить
корректность, пока он проходит несколько реальных границ кода.

Info Radar не заменяет второй репозиторий. Повторы в нём проверяют одну
архитектуру и один test stack. Вторым независимым кейсом остаётся Next.js для
TypeScript-задач; GovPL Monitor можно добавить позже как третье подтверждение
для API-ориентированной Python/React архитектуры. Внешний вывод должен назвать
оба проверенных репозитория и формы задач, а не обобщать результат на весь
"AI coding".

### Текущий статус Stage 0 (2026-09-16)

Для Info Radar подготовлены три независимые task card на одной pinned ревизии:

- `IR-RLS-01` — shared access boundary и регрессионный тест;
- `IR-SOURCE-DELIVERY-01` — один факт должен попасть в desktop и mobile UI;
- `IR-CONTENT-CATEGORY-01` — stored classification проходит через SQL contract
  и две reader-facing поверхности, не раскрывая внутренний reason.

Для `IR-RLS-01` завершён v2 quality gate: pinned revision, seed, task и evaluator
были заморожены до 15 fresh runs. Known-good control прошёл до и после серии,
а seed и source-only repair были отвергнуты в обоих случаях. Baseline, Code
Review Graph и Serena дали по 5/5 accepted patches. Для Code Review Graph
зафиксированы 15 MCP-вызовов, для Serena — 14. Даже 5/5 имеет широкий two-sided
95% interval 47.8%–100%, поэтому это наблюдение о конкретной shared access
boundary, а не доказательство равенства, security guarantee или преимущества
индекса.

Для `IR-CONTENT-CATEGORY-01` завершён final v4 quality gate: pinned revision,
complete seed, user-facing task brief и evaluator были заморожены до 15 fresh
runs. Known-good control прошёл до и после серии, а pristine seed был отвергнут
в обоих случаях. Результат: baseline 1/5 accepted, Code Review Graph 1/5,
Serena 0/5. У Code Review Graph зафиксированы 18 MCP-вызовов, у Serena — 41.
На этой одной cross-layer task индекс не продемонстрировал корректностного
преимущества над ordinary source navigation. Observed failure shapes: missing
paginated return field (7), mismatched closed vocabulary (2) и uncertain
suppression без mutation-sensitive test (4). Интервалы 0.5%–71.6% для 1/5 и
0%–52.2% для 0/5 слишком широки для рейтинга или причинного вывода.

`IR-SOURCE-DELIVERY-01` завершил v3 quality gate. В этой небольшой
TypeScript-задаче агент должен найти существующее bounded history, корректно
посчитать delivery только для `loaded > 0` и показать один факт в desktop и
mobile layout. Первые v2 candidate workspaces не считались: seed был
uncommitted inverse patch, и staged Git diff раскрывал историческое решение.
После этого был создан single-commit synthetic seed без Git history и staged
diff; task и evaluator не менялись. Known-good control прошёл до и после
серии, чистый seed и incomplete control были отвергнуты до и после серии.
Baseline, Code Review Graph и Serena дали по 5/5 accepted patches. Для Code
Review Graph зафиксированы 12 MCP-вызовов, для Serena — 13. Это ещё один
узкий факт: на таком малом UI impact path ordinary source navigation уже
достаточна, а два индекса не показали наблюдаемого correctness advantage.
Смотри `experiments/2026-09-15-info-radar-source-delivery-task-01/results-v3.md`.

Подробные methods, raw evaluator output и ограничения находятся в
`experiments/2026-09-15-info-radar-rls-task-01/results-v2.md`,
`experiments/2026-09-15-info-radar-content-category-task-01/results-v4.md`
и `experiments/2026-09-15-info-radar-source-delivery-task-01/results-v3.md`.
Все результаты отвечают только на quality gate. Они не содержат token, time,
build/refresh или freshness claim.

## Набор задач: работа разработчика, а не названия библиотек

Выберите реальные небольшие задачи из репозитория, где инструмент будет жить.
Каждая задача должна иметь один основной вопрос и собственный проверяющий
контракт.

| Задача | Что проверяется | Подходящий кандидат | Что служит истиной |
| --- | --- | --- | --- |
| API refactor radius | Найти точный символ, обновить direct production callers и нужные tests | LSP или code graph | Актуальный исходник, build и тесты |
| Regression и test decision | Изменить правило, определить затронутое поведение, добавить или обновить тест | LSP/graph для навигации; runner/coverage для решения о тестах | Поведение и тестовый runner |
| Cross-module impact | Пройти путь от входной точки до адаптера или конфигурации и изменить одну границу | Code graph или LSP | Исходник, конфигурация и contract test |
| Duplicate / structural decision | Найти известный повтор и безопасно извлечь его либо обосновать отказ | Structural search, например ast-grep | Source review и тесты |

Не нужно заставлять граф решать задачу поиска дубликатов или требовать от LSP
покрытия динамического runtime path. Способность агента выбрать source/test
fallback — положительный результат, а не поражение инструмента.

В первой серии лучше взять Python и TypeScript — языки, в которых работа идёт
сейчас. C# добавлять только для настоящего C# репозитория и его реальной
задачи: результат из Python или TypeScript ничего о нём не доказывает.

## Минимальная серия, которой можно доверять для локального решения

### Этап 0 — подготовить задачи и evaluator

Для каждого задания до первого candidate run сохранить:

- pinned revision и чистый checkout;
- user-facing brief без имён нужных файлов и готового решения;
- source-derived expected relationships, paths и test boundary;
- детерминированный evaluator вне candidate checkout;
- known-good patch, pristine checkout и неполный patch как три controls.

Known-good обязан пройти evaluator. Pristine и неполный patch обязаны не
пройти. Пока эти controls не работают, кандидатов запускать нельзя.

### Этап 1 — quality gate

Возьмите два реальных репозитория: один Python и один TypeScript. В каждом —
по три задачи: API refactor, regression/test, cross-module impact.

Для каждой пары «задача × подходящий инструмент» запустите:

- source baseline — 5 независимых fresh runs;
- index-assisted condition — 5 независимых fresh runs.

Это даёт **60 candidate runs**: 2 репозитория × 3 задачи × 2 условия × 5
запусков. Это discovery-пилот, а не доказательство эквивалентности. Он нужен,
чтобы найти ошибки цели, scope, freshness, evaluator-а и неожиданные отказы, а
не опираться на один удачный запуск.

После пилота не публикуйте формулировку «качество одинаковое». Пишите только
наблюдаемый факт, например: «5 из 5 запусков условия X прошли этот evaluator».
Даже 5 из 5 даёт широкий 95% exact interval: истинная вероятность успеха
может быть примерно от 48% до 100%. Равные 5/5 у baseline и индекса не
доказывают, что они равны.

Если для одной задачи действительно есть два разных кандидата, добавьте ещё 5
индексных запусков только к этой задаче. Не прогоняйте все инструменты через
все задачи ради таблицы.

### Этап 1B — подтверждающая серия качества

Кандидат, который прошёл discovery-пилот без критического поведения, получает
ещё 5 fresh runs в каждой проверенной ячейке. Получается **10 независимых
запусков на условие** и **120 candidate runs** для 2 репозиториев × 3 задач ×
2 условий × 10 запусков. Это уже пригодно для честного case study с
распределениями и exact confidence intervals, но всё ещё не позволяет
утверждать универсальное равенство или общий рейтинг.

Если цель — именно статистически показать, что индекс не ухудшает качество
более чем на заранее допустимую величину, нужен отдельный non-inferiority
design. До запусков фиксируются допустимое ухудшение, ожидаемая baseline
вероятность успеха, уровень уверенности и требуемая мощность; из них считается
размер выборки. Его нельзя честно назначить одинаковым для всех команд.

Важно различать две выборки. 120 candidate runs — это десять повторов шести
фиксированных task cards, а не 120 независимых видов разработки. Они хорошо
показывают повторяемость агента и инструмента на проверенных задачах. Они не
позволяют оценить, как часто польза встретится во всех Python, TypeScript или
C# проектах. Для более широкого утверждения после этой серии нужно расширить
корпус до 8–12 task cards в нескольких реальных репозиториях, сохраняя хотя бы
пять повторов на каждую пару «task × condition». Внешняя статья должна назвать
проверенные repos и task shapes, а не обобщать их как «AI coding» вообще.

Ориентир для risk-sensitive failure: при 30 независимых запусках без такого
сбоя верхняя односторонняя 95% граница его частоты всё ещё около 10%. Поэтому
10 чистых запусков — убедительный сигнал для инженерного решения, но не
достаточное основание для сильного safety-обещания.

### Этап 2 — серия повторной работы

Этап 1 отвечает на вопрос о качестве одной задачи. Чтобы проверить обещание
«рабочей памяти», нужен отдельный режим.

На одном репозитории подготовьте шесть независимых маленьких тикетов на одной
зафиксированной ревизии. Для каждого тикета запускается новая agent session,
чтобы память чата не стала скрытым преимуществом. В индексном условии один
готовый индекс доступен всем шести сессиям; в baseline каждая сессия начинает
с прямого поиска. Прогоните пять чередующихся последовательностей каждого
условия.

Итого: 6 тикетов × 2 условия × 5 последовательностей = **60 task runs**.
Три последовательности пригодны только как техническая репетиция стенда;
пять дают более полезную картину разброса, но всё ещё не превращают вывод в
универсальную статистику.
Первичная сборка индекса считается один раз на последовательность. Тот же
репозиторий и порядок задач чередуются между условиями, чтобы тёплый диск,
кэши или накопленное знание не достались одной стороне.

### Этап 3 — freshness challenge

Внутри каждой последовательности сделайте два контролируемых изменения,
которые меняют значимую связь: добавляют caller, меняют route/configuration
boundary или переносят test. После каждого изменения запросите индекс до и
после его update path.

Стенд фиксирует три состояния:

| Состояние | Допустимое поведение |
| --- | --- |
| Fresh | Индекс на нужной ревизии; связь проверена в source перед патчем. |
| Stale | Инструмент показывает устаревание либо агент не объявляет карту полной и переходит к source. |
| Partial / blocked | Исключения, ошибки или недоступный language service записаны; ответ не используется как полный. |

Один тихий пропущенный caller — достаточная причина пометить конфигурацию как
непригодную для relationship-sensitive change до исправления fallback или
refresh поведения.

## Что сохранять по каждому запуску

| Артефакт | Зачем он нужен |
| --- | --- |
| Commit, root, build flags, exclusions, tool и model version | Позволяет понять, что именно сравнивалось. |
| Fixed task brief и evaluator revision | Исключает изменение задачи по ходу серии. |
| Tool-call trace и возвращённый контекст | Доказывает, что индексный инструмент реально использовали. |
| Transcript или usage record | Даёт input/output/reasoning context, retries и время без догадок. |
| Final diff, tests, mutation result и source check | Доказывает или опровергает корректность патча. |
| Index manifest до и после изменения | Отделяет fresh, stale, partial и wrong-scope состояния. |
| Порядок запуска и состояние кэша | Помогает исключить скрытое преимущество одной стороны. |
| Короткая классификация failure | Wrong target, missed relationship, missing test, scope, stale, blocked, unrelated diff или fallback chosen. |

Публичный пакет должен хранить нейтральные пути и отредактированные transcripts.
Локальные абсолютные пути, ключи, токены, служебные логи и чужой исходный код
в нём не публикуются.

## Как считать результат

Сначала публикуется таблица качества, отдельно для каждой задачи и каждого
условия:

- accepted / rejected / blocked / partial;
- причина каждого rejection;
- все ли evaluator controls прошли;
- была ли source verification до изменения;
- был ли реально вызван индексный инструмент.

Только затем, среди accepted runs, публикуются абсолютные и распределённые
значения: model context, tool response size, retries, elapsed time, index build
и refresh time. Используйте median, min–max, exact confidence intervals для
pass rate и все исходные значения. Среднее само по себе скрывает один длинный
retry или build. Сравнение стоимости делайте по одинаковым задачам и
чередующемуся порядку; оно не должно маскировать различие в качестве патчей.

Не превращайте эти числа в общий score. Нужен capability profile:

| Вопрос | Подход | Качество | Цена жизненного цикла | Правило использования |
| --- | --- | --- | --- | --- |
| Например: exact references in TS | Serena | наблюдаемая доля accepted runs и known limits | setup + refresh + warm work | навигация, затем source check |
| Например: cross-module impact in Python | CRG | наблюдаемая доля accepted runs и known limits | setup + refresh + warm work | graph lead, source/test gate |

## Какая находка изменит наш вывод

Следующие наблюдения действительно дадут статье новый вес:

1. Baseline стабильно делает корректные патчи, а индекс не даёт измеримой
   выгоды. Тогда честный вывод: современному агенту в этой работе индекс не
   нужен.
2. Индекс сохраняет качество и уменьшает суммарную работу на последовательности
   после учёта build/refresh. Тогда можно сказать: он полезен как рабочая
   память для проверенных классов задач.
3. Индекс даёт меньше контекста, но чаще пропускает связи, выбирает неверную
   цель или создаёт лишние retries. Тогда это ложная экономия.
4. Польза есть лишь для одного языка, формы задачи или правильно настроенного
   scope. Тогда это capability profile, а не общий совет всем проектам.

## Что делать сначала

Не расширять текущий архив на новые 12 репозиториев. Подготовить три task cards
и evaluators для одного Python и одного TypeScript репозитория, затем выполнить
Этап 0 и первую пару baseline/index runs. Если controls или task definition
ломаются, исправить их до массовых запусков. Это даст более сильный материал
dля статьи, чем ещё одна широкая таблица retrieval-ответов.
